# elektrikaMarket — спецификация импорта PRODAT / PRICAT

**Версия:** 1.4  
**Дата актуализации:** 2026-10-05  
**Предыдущая версия:** 1.3 от 2026-10-05  
**Назначение:** постоянный технический контракт для разработки импорта каталога, характеристик, цен и остатков интернет-магазина `elektrikamarket.ru`.

> Эта версия сохраняет подтверждённые правила v1.1, учитывает полный анализ двух актуальных PRODAT: 148 882 исходные записи, 148 872 уникальных `SenderPrdCode`, 10 идентичных межфайловых дублей, а также сверена с официальными справочными PDF поставщика `rs_prodat.pdf` и `rs_pricat.pdf`.
>
> Если старые заметки, handoff-файлы или экспериментальный код противоречат этой спецификации, приоритет имеет **v1.2**, если отдельно не принято более новое решение.
>
> Важное уточнение v1.4: бизнес-логика цен подтверждена владельцем магазина и не пересматривается без конкретного противоречия в фактических данных.
>
> Для проекта:
> - `RetailPrice` — базовая цена для обычного клиента;
> - `Price2` — фактическая закупочная цена магазина с НДС;
> - `CustPrice` сохраняется как служебное поле, но пока не участвует в расчётах;
> - `MRC`, `BSP`, `Availability_MRC` пока не участвуют в расчётах.
>
> Официальные названия полей в PDF поставщика учитываются как справочные, но не отменяют подтверждённые бизнес-правила проекта.

## 0. Источники контракта и приоритет

Для PRODAT/PRICAT используются три уровня подтверждения:

1. фактические актуальные XML/ZIP поставщика;
2. официальные справочные документы поставщика `rs_prodat.pdf` и `rs_pricat.pdf`;
3. бизнес-правила магазина, отдельно утверждённые владельцем проекта.

Если фактический XML расходится с PDF, импортёр не должен молча угадывать смысл поля: расхождение фиксируется как предупреждение/ошибка и отдельно разбирается.

Официальный `rs_pricat.pdf` (версия документа 2.3) определяет:
- `RetailPrice` — базовая цена товара с НДС;
- `CustPrice` — цена клиента без НДС;
- `Price2` — цена клиента с НДС;
- `BSP` — базовая цена поставщика.

`Price2` отдельно подтверждён владельцем магазина как его фактическая закупочная цена с НДС. `RetailPrice` используется как базовая цена для обычного клиента. `CustPrice` сохраняется служебно, но в расчётах пока не используется. `MRC`, `BSP` и `Availability_MRC` пока не участвуют в расчётах.

## 1. Архитектурный принцип

PRODAT/PRICAT поставщика — внешние источники данных. Сайт хранит собственную нормализованную PostgreSQL-базу и не должен работать напрямую с большими XML при каждом пользовательском запросе.

Разделение ответственности:

- **PRODAT** → мастер-данные товара, каталожная принадлежность, ETIM-характеристики, изображения, документы, классификаторы, аналоги и сопутствующие товары;
- **PRICAT №1** → коммерческие данные, склад №1 и склад №3;
- **PRICAT №2** → коммерческие данные и склад №2;
- **наша БД** → нормализованные данные поставщика + собственные данные магазина, цены для клиентов, заказы, клиенты и служебная информация.

PRODAT не является источником актуального складского остатка.

- `PRODAT_369147_1312233182.zip`
- `PRODAT_369147_1312247470.zip`

Это две части одного логического массива, а не два независимых каталога.

## 3. Главный идентификатор товара

Для текущего единственного поставщика внешний ключ товара:

`SenderPrdCode`

Правила:

- один `SenderPrdCode` = один товар `Product`;
- PRODAT и оба PRICAT связываются по `SenderPrdCode`;
- `ItemID` не является основным ключом;
- `VendorProdNum`, EAN и другие поля не заменяют `SenderPrdCode`;
- внутренний `Product.id` генерируется PostgreSQL.

### Будущие поставщики

Пока в проекте один поставщик, существующий уникальный `Product.supplierCode` допустим. **До подключения второго поставщика** нужно отдельно спроектировать сущность уровня `SupplierProduct` с уникальностью `(supplierId, supplierCode)`. Не следует считать код одного поставщика вечным глобальным идентификатором всего магазина.

## 4. Общие требования к PRODAT-парсеру

Production и dry-run обязаны использовать один общий потоковый парсер и один нормализатор. Различаться должен только этап сохранения.

Обязательные правила:

1. XML обрабатывается потоково; целый XML не загружается в память.
2. Вложенность, массивы, текст и пустые значения не должны теряться.
3. Структуры, которые могут встречаться 0, 1 или N раз, всегда нормализуются в список на уровне нормализатора.
4. Кодировка определяется по BOM/XML declaration; текущие два PRODAT объявлены как `windows-1251`.
5. Нельзя жёстко считать, что все будущие файлы обязательно Windows-1251.
6. Числа веса/габаритов сначала сохраняются как исходные строки и только затем безопасно преобразуются в `Decimal`; промежуточное преобразование через JavaScript `Number` не использовать для значений, где важна точность.
7. Одинаковые `SenderPrdCode` сравниваются по нормализованному полному содержимому: идентичный дубль пропускается, различающийся — конфликт.
8. Порядок ZIP-файлов не должен определять победителя при конфликте.
9. Production-парсер должен также отдавать метаданные заголовка документа (`DocType`, `SenderGln`, `ReceiverGln`, `Currency`, `DocumentNumber`, `DocumentDate`, кодировку и источник файла).
10. ZIP/XML не коммитятся в Git; для воспроизводимости импорта сохраняются имя источника и контрольная сумма.

### 6.2. Вес и габариты

`Weight`:

- `WeightUnit`;
- `Value`.

`Dimension`:

- `DimensionUnit`;
- `Depth`;
- `Width`;
- `Height`.

В текущих данных вес и габариты формально присутствуют всегда, но у десятков тысяч товаров значения равны нулю. Нулевое значение не следует автоматически считать реальным физическим размером.

Встречаются значения вида `1.`, `0.` и до 10 знаков после точки. Хранение должно поддерживать эту точность.

Вес и габариты нужны для будущего упаковочного модуля и расчёта доставки. Преобразование в единицы конкретного перевозчика выполняется отдельно от хранения исходных данных.

## 7. Категории сайта

### 7.1. Две разные классификации

PRODAT содержит две независимые классификации:

**Техническая ETIM-классификация:**

`ParentProdCode / ParentProdGroup → ProductCode / ProductGroup`

В текущем наборе:

- 70 технических групп;
- 1 413 технических классов;
- каждый класс имеет только одного родителя;
- конфликтов названий не обнаружено.

Эта классификация нужна прежде всего для ETIM-характеристик и технической логики.

**Каталог поставщика `RsCatalog`:**

```text
Level4 — верхняя категория
  Level3 — раздел
    Level2 — конечная категория
```

В текущем наборе:

- 12 категорий Level4;
- 34 категории Level3;
- 198 категорий Level2;
- конфликтов названий и родителей не обнаружено;
- у 20 610 записей с `RsCatalog` отсутствует Level4;
- у 6 571 исходной записи `RsCatalog` отсутствует полностью.

### 7.2. Решение для публичного каталога

**Публичное дерево сайта строится по `RsCatalog`.**

ETIM `ParentProdCode/ProductCode` не смешивается с `RsCatalog` в одном дереве категорий.

Правила:

- если есть Level4 → строим `Level4 → Level3 → Level2`;
- если Level4 отсутствует, Level3 временно становится корнем;
- товар привязывается к самой глубокой доступной категории `RsCatalog`;
- названия поставщика могут обновлять отображаемое имя по принятой политике, но не являются идентичностью категории;
- ручные изменения структуры/SEO в админке должны иметь приоритет над автоматическим изменением поставщика.

### 7.3. Товары без `RsCatalog`

Старая рабочая заметка предполагала создание публичных fallback-категорий по `ParentProdCode/ProductCode`. Полный анализ показал, что такие данные технически детерминированы, но содержат служебные классы вроде «Позиции без привязки к категории» и «Прочие товары».

**Решение v1.1:** технические ETIM-коды не превращаются автоматически в публичную ветку `RsCatalog`.

Товар без usable `RsCatalog`:

- сохраняется в БД;
- получает служебное состояние/категорию уровня «Требует категоризации»;
- сохраняет `ParentProdCode`, `ParentProdGroup`, `ProductCode`, `ProductGroup` для последующей автоматической или ручной категоризации;
- не должен порождать фиктивные публичные категории только ради внешнего ключа.

### 7.4. `Category.sourceKey`

`sourceKey` — стабильная идентичность узла внешнего каталога, не зависящая от названия и slug.

Для `RsCatalog` использовать ключ **конкретного узла**, например:

```text
rsv:catalog:L4:1
rsv:catalog:L3:14
rsv:catalog:L2:69
```

Это правило **заменяет** старый экспериментальный формат, где в один `sourceKey` включалась вся комбинация L2/L3/L4.

`slug` не должен автоматически меняться только потому, что поставщик переименовал категорию.

## 8. `RsCatalog` в товаре

Помимо `Product.categoryId`, полезно сохранять исходную структурированную принадлежность `RsCatalog` для аудита и повторной нормализации.

Рекомендуемое логическое представление:

```json
{
  "level4": { "id": "1", "name": "Освещение" },
  "level3": { "id": "14", "name": "Светотехника" },
  "level2": { "id": "69", "name": "Светильники наружного освещения" }
}
```

Текущее строковое `Product.rsCatalog` следует считать временным решением. Точный Prisma-тип (`Json?` или отдельная служебная модель) утверждается перед production-миграцией.

## 9. ETIM-характеристики

Источник:

`FeatureETIMDetails/FeatureETIM`

Поля:

- `FeatureCode`;
- `FeatureName`;
- `FeatureValue`;
- `FeatureUom`.

Полный проход текущего PRODAT:

- элементов `FeatureETIM`: **4 120 385**;
- с пустым `FeatureValue`: **2 038 631**;
- с непустым значением: **2 081 754**;
- различных кодов характеристик: **5 990**;
- различных обозначений единиц: **90**;
- повтор одного `FeatureCode` внутри одного товара: **0** в текущем наборе;
- 16 кодов имеют более одного варианта названия.

### Правила хранения

1. Ключ характеристики — `FeatureCode`, а не название.
2. Исходные `featureCode`, `featureName`, `featureValue`, `featureUom` сохраняются.
3. Суффиксы вроде `_1` являются частью кода и не удаляются.
4. Пустые `FeatureValue` **не создают миллионы бесполезных `ProductFeature`**.
5. При полном обновлении товара пустое значение может означать удаление ранее импортированного значения этой характеристики; для частичной выгрузки нужна отдельная семантика.
6. Не создавать жёсткие колонки Product под характеристики конкретных категорий.
7. Для фильтрации допустимы производные nullable-поля вроде `valueNumber`, `valueBoolean`, `valueType`, но только при достоверной типизации.
8. Нельзя определять официальный тип ETIM только по внешнему виду строки: `10` может быть числом либо значением списка.
9. Для полной типизации нужен отдельный справочник ETIM соответствующей версии.
10. Порядок характеристик следует сохранять (`sortOrder`).

## 10. Штрихкоды

Источник:

`EAN.Value` + `EAN.Description`

В текущем PRODAT:

- у товара может быть до 9 пар;
- массивы `Value` и `Description` имеют совпадающую длину;
- пары соединяются **по индексу**;
- EAN хранится строкой, ведущие нули не теряются.

В БД один и тот же barcode у одного товара не должен размножаться при повторном импорте.

## 11. Изображения, документы и видео

### Изображения

`Image.Value` → `ProductImage`.

Правила:

- URL — внешний источник;
- порядок сохраняется;
- одинаковый URL у одного товара не дублируется;
- бинарные изображения в PostgreSQL не загружаются.

### Сертификаты

`CertificateInfo.Certificate`:

- `CertificateType`;
- `CertificateURL`.

Хранятся как `ProductDocument`.

### GOST / TY

`GOST` и `TY` встречаются как внутри `CertificateInfo`, так и непосредственно в `DocDetail`.

Правило v1.1:

- собирать непустые значения из обоих мест;
- разные значения не перезаписывать молча;
- хранить все уникальные значения либо в списках стандартов, либо в отдельной нормализованной структуре;
- точная Prisma-реализация утверждается перед миграцией.

### Прочие документы

- `CatalogBrochure.Value` → `ProductDocument(type="catalog")`;
- `Passport.Value` → `ProductDocument(type="passport")`;
- `Video.Value` → на первом этапе допустимо `ProductDocument(type="video")`.

Пустые URL не сохраняются.

### Аналоги

`Analog.ItemCode` → связь типа `analog`.

### Сопутствующие

`RelatedProd.ItemCode` → связь типа `related`.

В текущем наборе часть целевых кодов отсутствует среди импортируемых товаров:

- пусто — 1 005.

Поэтому `Boolean?` недостаточен.

**Правило v1.1:** сохранить исходный статус без потери информации. Для текущей реализации предпочтителен `String?` либо enum с отдельным `CHECK` и nullable для отсутствия. Нельзя превращать `check` в `true/false`.

## 15. Три склада

### Склад №1

`PRICAT №1 → DocDetail/QTY`

### Склад №2

`PRICAT №2 → DocDetail/QTY`

### Склад №3

`PRICAT №1 → DocDetail/SupOnhandDetail/PartnerQTY`

Дополнительные данные:

- `PartnerUOM`;
- `LastUpdDate`;
- `EstimatedArrivalDate`.

Эти поля относятся к `SupOnhandDetail`, поэтому в целевой модели их нельзя бездумно хранить как глобальные свойства `Product`; они должны быть привязаны к соответствующему источнику/складу или отдельной записи состояния поставщика.

### `SumQTY`

Полностью игнорируется.

Общий доступный остаток при необходимости вычисляется как:

`Stock1 + Stock2 + Stock3`

## 16. Доступность товара

Товар считается доступным для активной продажи, если:

`Stock1 > 0 OR Stock2 > 0 OR Stock3 > 0`

Если все три остатка равны нулю:

- `Product` не удаляется;
- товар остаётся в БД;
- при возвращении остатка снова становится доступным.

Конкретное правило показа карточки товара без остатка на сайте может быть расширено позже; физическое удаление Product с этим не связано.

---

## 17. Multiplicity

`Multiplicity` — кратность покупки у поставщика, не обязательно количество в упаковке.

Примеры:

- `1` → 1, 2, 3…;
- `3` → 3, 6, 9…;
- `10` → 10, 20, 30…

`ItemsPerUnit` и `Multiplicity` — разные понятия.

UI количества должен учитывать шаг `Multiplicity` и валидировать ручной ввод.

## 18. Цены

### Подтверждённая бизнес-логика

Для нашего магазина действуют следующие правила:

- `RetailPrice` — базовая цена для обычного клиента;
- `Price2` — фактическая закупочная цена магазина с НДС;
- `CustPrice` — сохраняется как служебное поле, но пока не используется в расчётах;
- `MRC`, `BSP`, `Availability_MRC` — пока не участвуют в расчётах.

Эти правила уже подтверждены владельцем магазина и не должны пересматриваться только из-за формулировок в PDF поставщика.

### Обычный клиент

Базовая цена:

`RetailPrice`

Для зарегистрированных обычных клиентов может применяться внутренняя шкала скидок от суммы заказа.

Пример:
- от 10 000 ₽ → −2%;
- от 20 000 ₽ → −3%.

Шкала настраивается в админке.

### Индивидуальный клиент

Если клиенту назначена индивидуальная наценка:

`Price2 × (1 + индивидуальная наценка / 100)`

Например:

`Price2 = 567,80 ₽`
`наценка = 15%`
`цена клиента = 653,97 ₽`

При индивидуальной наценке общие скидки от объёма не применяются.

Клиент видит только рассчитанную цену.

`Price2` не показывается клиенту как закупочная цена.

Историю цен на текущем этапе отдельно не ведём. Цена оформленного заказа фиксируется в `OrderItem` и далее не меняется.

## 19. Правила обновления PRODAT

### Новый товар

Если `SenderPrdCode` отсутствует:

- создать Product;
- создать/связать Brand;
- определить категорию;
- создать непустые характеристики;
- создать штрихкоды;
- создать изображения;
- создать документы;
- сохранить связи либо unresolved relations.

### Изменившийся товар

- обновлять только реально изменившиеся данные;
- не создавать дубли дочерних записей;
- синхронизировать характеристики, штрихкоды, изображения и документы по принятой семантике полного импорта.

### Неизменившийся товар

Не выполнять лишние записи в БД.

### Исчезнувший из нового PRODAT

**Не удалять автоматически и не отключать только по факту отсутствия.**

Отсутствие товара в конкретном наборе PRODAT само по себе не доказывает, что товар снят с продажи.

## 20. Полный и частичный импорт

До production необходимо явно различать:

- **полный срез** каталога;
- **частичную/инкрементальную** выгрузку.

Для полного среза допустима синхронизация дочерних supplier-owned данных с удалением значений, которые исчезли/стали пустыми.

Для частичного файла отсутствие поля или товара **не означает удаление**.

Importer обязан знать тип семантики текущего файла до применения destructive sync-операций.

---

## 21. Ежедневный импорт

Общая архитектура:

```text
FTP / внешний источник
  → проверка файлов и контрольных сумм
  → Import Worker
  → streaming parser
  → validation + dedup
  → normalization
  → PostgreSQL
  → журнал результата
```

### PRODAT

1. найти актуальные части;
2. проверить изменения по metadata/размеру/SHA-256;
3. если срез не изменился — не обрабатывать повторно без причины;
4. скачать все части текущего среза;
5. логически объединить;
6. проверить конфликтующие дубли;
7. нормализовать;
8. upsert;
9. разрешить дочерние данные и связи;
10. провести итоговую сверку;
11. записать результат запуска.

### PRICAT

Для каждого источника/склада независимо:

1. найти новый файл;
2. проверить изменение;
3. обработать;
4. обновить соответствующий склад;
5. обновить коммерческие поля;
6. записать результат.

Имена файлов не считаются постоянным контрактом.

## 26. Требуемые изменения текущей Prisma-схемы перед production-импортом

Полный аудит PRODAT подтвердил, что текущая схема является хорошей основой, но требует доработки.

### Подтверждённые требования

1. `Category.sourceKey` должен существовать в SQL-миграциях и соответствовать новой узловой схеме ключей `rsv:catalog:Lx:id`.
2. `Product.country String?` недостаточен: товар может иметь несколько стран.
3. `Product.itemsPerUom Decimal?` имеет неверный тип: фактические значения текстовые.
4. Нужны вес, единица веса, три габарита и единица габаритов с точностью до 10 знаков после точки.
5. Нужен `Product.series`.
6. Нужно хранить все уникальные GOST/TY из обоих мест XML.
7. `Product.labelledItemChz Boolean?` недостаточен; исходный статус должен сохраняться без потерь.
8. `Product.rsCatalog String?` следует заменить структурированным хранением либо оставить только как временное legacy-поле после появления нормализованной структуры.
9. Дочерние таблицы должны иметь достаточные уникальные ограничения для идемпотентного повторного импорта.
10. `ProductFeature` нужен `sortOrder`; типизированные производные поля для фильтров — отдельным этапом.
11. `ProductRelation.relatedId` не может быть обязательным единственным представлением внешней связи: нужны unresolved relations.
12. Нужны `ImportFile`/`ImportRun` и журнал ошибок/предупреждений.

### Предпочтительное направление, которое ещё нужно утвердить перед миграцией

- страны: PostgreSQL `String[]` либо нормализованная связь;
- GOST/TY: массивы строк либо отдельная таблица стандартов;
- `RsCatalog`: `Json?` как raw snapshot + `categoryId` как рабочая связь;
- `LabelledItemCHZ`: `String?` либо enum;
- ETIM typed values: `valueNumber`, `valueBoolean`, `valueType` только после надёжной типизации;
- unresolved relations: отдельная таблица либо модель связи с `targetSupplierCode` и nullable `relatedId`.

**До отдельного утверждения точной Prisma-модели эта спецификация не является разрешением автоматически создавать миграцию.**

## 27. TypeScript / модуль импортера

Текущий общий парсер был реализован как `prodat.cjs` из-за проблемы запуска `tsx`, а не потому, что CJS обязателен архитектурно.

Целевое направление:

- импортный код — типизированный TypeScript;
- общий parser/normalizer используется dry-run и production;
- добавить явные типы сырого XML, нормализованной записи, source metadata и результатов dedup;
- добавить проверку типов `tsc --noEmit`;
- проблему `tsx` рассматривать отдельно от архитектуры парсера.

Переход с CJS не должен одновременно смешиваться с изменением бизнес-правил импорта без необходимости.

## 29. Рекомендуемый production pipeline

```text
ZIP + SHA-256
  → metadata XML
  → общий streaming parser
  → structural validation
  → duplicate/conflict check
  → normalization
  → validation business rules
  → brands + categories
  → Product upsert
  → barcodes/features/images/documents
  → unresolved + resolved relations
  → PRICAT prices/stocks отдельным этапом
  → reconciliation
  → ImportRun result
```

Пакетные транзакции должны быть ограниченного размера; одна транзакция на все 148+ тыс. товаров не является обязательной целью.
