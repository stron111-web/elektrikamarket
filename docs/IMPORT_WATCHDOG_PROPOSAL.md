# Отдельный watchdog импортов — проект, не установлен

Основание: issue #4, комментарии 6952308827, 6951276162 и 6951290834.
Получатель согласован владельцем: stron1@mail.ru. SMTP-отправитель и секреты
не предоставлены; письма, включая тестовые, не отправлялись.

watchdog-model.cjs — чистый прототип контроля дедлайна, отсутствия прогресса,
просрочки успешной проверки FTP и дедупликации инцидентов. Он не получает
update.lock, не подключается к БД, SMTP и Docker и не останавливает процессы.
Он должен запускаться отдельно от импортёра, иначе зависший lock заглушит тревогу.

План интеграции, требующий испытаний перед отдельным разрешением на установку:

1. Подключить существующий onProgress к атомарному heartbeat-файлу 0600 в закрытом
   state: runId, source, стадия, счётчики строк/байт, lastHeartbeatAt, lastProgressAt.
   Пустой heartbeat не продлевает progress deadline. Валидация, разбор, spool,
   SQL-батчи и публикация дают свои реальные показатели. Без raw записей/секретов.
2. Общий deadline + watchdog без прогресса должны действовать на всю цепочку,
   включая ожидание следующего chunk, file write, SQL, cleanup. Прерывать через
   AbortSignal, закрывать потоки, rollback/release. Обработчик TERM и отказ
   cleanup проверять отдельно, не рассчитывать на finally при сигнале.
3. Контроллер задания отслеживает конкретный container ID. Нельзя ограничиться
   timeout для Docker CLI: он способен оставить живой контейнер. Никакого
   автоматического SIGKILL; после TERM и истечения ожидания — удержание публикации,
   диагностика и письмо. Не удалять lock и uncertain-COMMIT маркеры.
4. Отдельный host-side observer читает только безопасные status/heartbeat файлы,
   работает без общего flock. Проверяет PRICAT1/2 раздельно (интервал 3 часа),
   PRODAT (12 часов). Успешный NO_REMOTE_CHANGE обновляет успешную проверку;
   отсутствие новой публикации само по себе не является инцидентом.
5. Значения grace/stall/max-run обосновать измерениями на копии с реальными
   файлами. В модель не зашиты производственные значения; параметры тестов — fixtures.
6. Отдельный таймер наблюдения предлагается раз в минуту; пока он не установлен.
   Читаемые adapter-форматы реального state ещё нужно привязать и проверить.
7. SMTP через существующую корпоративную VK WorkMail после подтверждения
   отправителя/доступа. Реквизиты только в закрытом VPS-файле, не argv/логи/Git.
   TLS, проверка сертификата, адресат фиксирован. Состояние доставки хранить атомарно.
   Одно предупреждение на инцидент, затем одно восстановление. После ошибки SMTP
   не отмечать письмо отправленным; повтор с тем же ID, без множества инцидентов.
8. Письмо содержит только источник, причину, последнюю успешную проверку, время
   Самары UTC+4 и ID инцидента. Нет токенов, URL БД, сырых XML и закупочных цен.
9. Проверить crash между SMTP acknowledgement и записью состояния: SMTP не даёт
   строгой exactly-once доставки. Нужна durable outbox/идемпотентность получателя
   либо явно зафиксированное ограничение. Recovery-доставка также требует outbox:
   чистая модель показывает переход, но сама не гарантирует доставку письма.

В этой ветке подготовлены только модель, шесть локальных тестов и данный план.
Не реализованы: адаптеры реальных файлов, AbortSignal во всех потоках импортёра,
host-controller, durable outbox, SMTP transport и timer. Их нельзя считать
работающей защитой или почтовым мониторингом. На VPS ничего не развёрнуто.
