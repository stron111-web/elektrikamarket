# Поиск каталога: PostgreSQL FTS и pg_trgm

Статус: реализовано и проверено **локально** 02.11.2026 в codex/catalog-fts от 7ca5122.
На VPS SQL не применялся, сайты/PRICAT/PRODAT/preview/friend не менялись. Push/merge/deploy не выполнялись.

## Устройство

- Одна PostgreSQL GENERATED ALWAYS STORED колонка products.searchVector (tsvector), один новый GIN-индекс. Новых таблиц, баз, сервисов и поискового сервера нет.
- PostgreSQL russian: морфология названий и префиксы tsquery. Вес B — исходное название; C — техническая нормализация названия; A — код РС и артикул. Явные regconfig исключают зависимость от default_text_search_config.
- Все введённые слова комбинируются AND, порядок слов произвольный. Для сохранения прежнего поиска внутри слова есть индексируемый буквальный ILIKE по названию/артикулу. Артикул с дефисами ищется буквально, с экранированием LIKE wildcards; он не отправляется в fuzzy.
- Технические токены используют simple и точную фразу <-> после ограниченной нормализации: 16А/16A → 16 a; 10кА/10kA → 10 ka; C16/С16 → c 16. Числа не имеют префикса и не участвуют в приблизительном поиске. Фраза не позволяет объединить 17 из модели с A из другого места и выдать это за 17А.
- Одиночное число сохраняет буквальный поиск фрагмента кода/артикула. В многословном запросе числовые лексемы точные: 16 не становится 160 или 016. Никакой автоматической подмены чисел/артикулов.
- При ненулевом строгом результате approximate-ветка не выполняется. При нуле: существующий GIN pg_trgm имени и оператор %>, word_similarity_threshold=0.3 **только SET LOCAL**, слово не короче 5 букв, максимум одно нечётко совпавшее слово. Все остальные ограничения, числа, артикула, категория/бренд и снимок обязательны. Нет собственного словаря/расстояния Левенштейна/очереди/сервиса.
- Сначала точный полный артикул или код, затем штатный ts_rank_cd(...,32) по объединённому tsquery, затем стабильный Product.id. В fallback используется также штатный word_similarity. UI помечает близкие текстовые совпадения.
- Каталог всегда соединяется с активным assortment_items. Count/page/offer читаются в одной REPEATABLE READ READ ONLY транзакции; фильтры применяются до count и пагинации, параметры связаны через postgres tagged templates. availability=all обхода не создаёт.
- Вектор поддерживается PostgreSQL при INSERT/UPDATE названия/кода/артикула. PRICAT-импортёр и снимок не изменены, дополнительной фоновой перестройки нет. На PRODAT возрастает стоимость обновления Product, её абсолютное время на реальном новом PRODAT не измерялось.

Текущий main/preview могут иметь другие изменения — интеграция отдельная, без force push и автоматического изменения preview/friend.
2. Read-only preflight VPS: версия/локаль/pg_trgm, наличие русской конфигурации, актуальная схема/rows/indexes/свободное место, read-only роли. Сохранить свежий backup и доказать восстановимость на изолированной копии.
3. Согласовать краткое окно для общей БД test/preview. ALTER TABLE ADD GENERATED STORED переписывает Product и требует ACCESS EXCLUSIVE; GIN строится в той же транзакции. Возможна временная задержка чтения **обоих** сайтов, хотя их код не меняется. Не обещать online-миграцию без блокировки.
4. Удержать существующий lock административного обновления, исключить параллельный PRICAT/PRODAT и ручные правки. Расписание/импортёры не переписывать. 5. ANALYZE products, проверить count/мастер-хеш/индекс/точность запросов и права SELECT. Если Product выдан column-wise, добавить только SELECT(searchVector); покупные цены/запись не выдавать. Новый вектор не содержит коммерческих/персональных данных.
6. Только после успешной подготовки БД обновить **только согласованный web**, не PostgreSQL/Caddy/preview. Повторить реальные запросы, фильтры, страницы/карточки/авторизацию и замеры. Отдельное включение preview — через Андроника, без вмешательства в его ветку.
7. Откат приложения — прежний web-image; добавленные функции/колонка/индекс могут безопасно остаться, старый reader их не использует. Не удалять Product/цены/остатки/снимки. Ошибка SQL до COMMIT оставляет старую схему. Удаление производных структур, если понадобится, отдельно согласовать; не выполнять автоматический DROP/restore поверх рабочей БД.

## Границы

Это текстовый поиск, не семантическая модель электрических характеристик. Нормализация ограничена указанными обозначениями; общей транслитерации/синонимов брендов нет. Fuzzy может вернуть текстово близкое нерелевантное слово; порог0.3, минимум5 букв и один нечёткий токен зафиксированы и требуют продуктовой проверки на других реальных запросах. Второго fuzzy-слова не допускаем. После появления любых строгих результатов fallback не смешивается с ними; достаточно совпавшего допустимого артикульного фрагмента, без приблизительной подмены цифр.

При изменении функции нормализации в будущем недостаточно CREATE OR REPLACE: stored-вектор уже вычислен, нужна отдельная согласованная миграция пересчёта. Изменение словаря PostgreSQL также требует проверки переиндексации/производных значений. Snapshot и торговые правила не дублируются в поиске.

Стандартные механизмы и параметры: [PostgreSQL17 FTS, префиксы и ts_rank_cd](https://www.postgresql.org/docs/17/textsearch-controls.html), [pg_trgm](https://www.postgresql.org/docs/17/pgtrgm.html).

вне Git. Все подключения benchmark имеют default_transaction_read_only=true;
схема и индекс должны быть подготовлены заранее только на этой копии.
