# Проект PRICAT: проверка по кодам вместо порогов одного испытания

Статус на 17.11.2026: **проект и локальный проверяемый прототип**.
Ветка `codex/pricat-code-safeguards`, база `8c5d619`.
Не установлен на VPS; существующие update.cjs/importer/reader/cron/config не менялись.
Ни production-, ни dry-run-импорт с подключением к БД не запускался.
Проверка старых сводок не является разрешением публикации.

## Проблема и целевое поведение

Постоянные пределы 4,3115% и 0,03956331% были получены Codex из одного
испытания, без подтверждённого согласования чисел владельцем. Во время
перемаркировки сокращение источника может быть легитимным. Оно само по себе
не является доказательством неполной или ошибочной выгрузки.

Новая логика не назначает другие проценты взамен старых. Она проверяет
техническую целостность, конкретные коды, запись каждого источника и результаты
канонической торговой логики. Количество и доли — диагностика, не разрешение/запрет.

## Предлагаемая последовательность

1. Получить согласованную пару обычным механизмом FTP metadata-first; при
   неизменности версии не скачивать заново. Сохранить привязку источников и SHA.
2. Сохранить SHA/size/CRC, ровно один XML в ZIP, строгий XML/кодировку/DocType,
   получателя/источник, DocumentNumber/DocumentDate, стабильность файлов,
   целостность пары, технические ограничения ресурсов, блокировки и маркеры COMMIT.
3. Разобрать каждый источник штатным потоковым readPricat и normalizePricat.
   Код без однозначного SenderPrdCode блокирует файл: невозможно безопасно
   определить, какую позицию изолировать. Пустой источник не принимать автоматически.
4. По каждому источнику независимо сравнить **множества SenderPrdCode**:
   retained / added / absent. Отдельно показать изменённые записи, идентичные
   дубли, конфликтующие коды, невалидные записи и изменения UOM/упаковки.
   Сравнивать с принятыми файлами активного snapshot, не с последним неуспешным
   скачиванием, product_stocks или общей таблицей products.
5. На действующей базе дополнительно классифицировать каждый affected code:
   есть ли Product, архив, какая цена выбрана, какие склады доступны, quarantines,
   manual/locked и действующая UOM/упаковка. Эту часть выполняет существующий
   store/availability; прототип её не заменяет и не имитирует SQL в JavaScript.
6. Корректные записи обрабатывает существующий импортёр; дефект конкретного
   известного кода изолируется для его источника/склада, а не процентным отказом пары.
7. Новый snapshot публикуется существующей атомарной транзакцией только после
   сверки baseline, настроек и классификации изменений по кодам. При технической
   ошибке никакого частичного COMMIT или SHA-success. Сохранить прежний snapshot.

CRC и закрывающий тег XML доказывают техническую целостность, **не полноту
ассортимента поставщика**. Файл с корректным XML, из которого удалили часть
целых DocDetail, может пройти CRC/парсер. Без контракта полного снимка или
подтверждения конкретной пары нельзя автоматически отличить это от перемаркировки.

## Что делать с отсутствующими товарами

**Правило утверждено владельцем 17.11.2026**, повторного согласования не требует:
https://github.com/stron111-web/elektrikamarket/issues/4#issuecomment-6952160868

Product/PRODAT, изображения, характеристики, документы и связи не удалять.
Товар может остаться доступным через другой корректный источник/склад.

Существующее правило 02.11: полный принятый PRICAT1 заменяет supplier-остатки
stock1/stock3, PRICAT2 — stock2. Отсутствующий код/пустое количество даёт ноль
только своему supplier-складу; manual/locked не переписываются, а неподтверждённый
защищённый остаток исключается каноническим карантином. Это уже реализованная
архитектура; проект не предлагает менять её молча.

Разделяем **подтверждённое отсутствие** и **неподтверждённый статус файла**:

| Ситуация | Предлагаемое действие |
|---|---|
| Подтверждён полный снимок, код действительно отсутствует | Штатный replaceMissingStocks только своих складов, с прежней защитой manual/locked |
| Полнота источника не подтверждена | Не публиковать файл как полный; отсутствие кода не доказывает нулевой остаток. Получить техническое подтверждение статуса файла |
| Конфликт/ошибка записи кода | Карантин этого кода в этом источнике; не считать отсутствующим и не выбирать произвольный дубль |
| Другой источник корректен | Сохранить возможность продажи с него по каноническим правилам |

Старое количество не сохранять ради истории и не использовать как запасной
активный supplier-остаток после подтверждённого отсутствия. Реализация должна
дать 0 либо исключить активное предложение соответствующего источника. Защита
manual/locked не должна оставлять неподтверждённый supplier-остаток продаваемым:
сохранять каноническое исключение через карантин защищённых supplier-строк.

Если код появился в следующем подтверждённом полном снимке, обрабатывать его
фактические новые цены/остатки обычным импортёром и автоматически возвращать
в продажу при выполнении остальных правил. Не подставлять прежнее количество
и не требовать ручного снятия исчезновения только из-за его истории.

Прежнее предложение «сохранить числовой stock и временно блокировать absent»
снято. Для неполного/непроверенного файла вместо частичной публикации с таким
режимом — блокировка публикации источника до подтверждения его статуса.
Сохранённый при техническом отказе старый snapshot не становится от этого свежим;
его возраст должен отражаться в эксплуатационном мониторинге.

Не добавлять новые цены/конверсии и не менять торговый приоритет
MANUAL → PRICAT2 → PRICAT1. Отдельно нужно решить свежесть цены отсутствующего
кода: старый источник может дать выбранную цену даже при наличии другого склада.
Нельзя решить это одним обнулением stock и объявить вопрос закрытым.

## Конфликтующие дубли и существенные ошибки

- Идентичные записи сворачиваются; дубли не создают дополнительные товары.
- При разных значениях одного SenderPrdCode не выбирать первую/последнюю:
  изолировать весь код конкретного источника, сохранить диагностику всех вариантов.
- Количество конфликтов и его доля не блокируют все остальные корректные записи.
- Ошибочная цена, отрицательное/непредставимое количество, неоднозначная упаковка,
  несовместимые валюты — карантин идентифицированной записи.
- UOM/упаковку относительно существующего товара проверяет прежний pricat-store;
  не конвертировать NMP/ItemsPerUnit/PartnerQTY произвольно.
- Некорректный XML/ZIP/кодировка, неоднозначная идентичность источника/записи,
  незавершённая передача, нарушенная пара, неопределённый COMMIT — блокирующая ошибка.
- Устаревание источников, пустой весь ассортимент и массовое отсутствие по причинам,
  которые нельзя классифицировать по кодам, требуют отдельного решения, а не нового процента.

## Все связанные ограничения, которые надо заменить при интеграции

Недостаточно удалить два guard из dryGates:

| Нынешний guard | Проект замены |
|---|---|
| SOURCE_RECORD_DROP / minSourceRecords, откалиброванный по одному запуску | Непустой технически корректный источник + точные множества кодов + подтверждение полноты/отсутствия |
| SOURCE_ISSUE_RATE | Поимённый карантин идентифицированных дефектов; отсутствие кода блокирует источник |
| KNOWN_PRODUCT_COVERAGE_DROP | Перечень утраченных известных товаров и объяснение по конкретным кодам |
| maxRemovedFraction / maxStockCellLossFraction | Для каждого исчезнувшего оффера/склада — доказанная причина: absent, ноль, карантин, архив, отсутствие цены и т.д.; необъяснённые изменения блокируют |
| maxChangedPriceFraction, maxPriceChangeFactor, maxQuantityChangeFactor, полученные из того же опыта | Поэлементная точная арифметика, валюта, UOM, защитная наценка и provenance; новые абсолютные/договорные лимиты вводить только после отдельного согласования |

Числовые скачки цены/количества показывать в отчёте. Ни произвольный новый процент,
ни другое столь же произвольное отношение не должны подменять бизнес-решение.
Глобальный пустой candidate snapshot не публиковать автоматически; сценарий
полного прекращения поставок требует отдельно согласованной процедуры.

Для воспроизводимости решения о подтверждённом отсутствии привязать к точным
SHA, source и активному snapshot. Изменился любой из них — проверить заново.
Это не обязательно ручное одобрение каждой ежедневной пары: после однократного
утверждения владельцем контракта полного снимка для конкретного FTP-канала
подтверждение может автоматически формироваться по утверждённой версии политики
и техническим доказательствам конкретного набора. Сейчас такой контракт в новой
политике не активирован; прототип не подменяет его успешным чтением XML.

## Что реализовано в этой ветке

- source-review.cjs — потоковый офлайн-анализ с существующим парсером и нормализатором,
  проверкой ZIP CRC, стабильности SHA, множествами кодов, карантином и планом отсутствия.
- reviewDrySummary — проверяемый прототип новой непроцентной проверки согласованности
  dry-summary. Возвращает SOURCE_STATS_ACCEPTED и **publishAllowed=false**.
- planAbsence — декларативный план по SHA/source/snapshot; никогда ничего не пишет.
- review-files.cjs — диагностический CLI без .env, PostgreSQL и FTP.
- source-review.test.cjs — 16 тестов без БД.

**Не реализовано/не заявляется:** подключение новой политики к production update.cjs,
детальный SQL-аудит всех исчезнувших
офферов candidate snapshot и проверка полной новой production-цепочки на копии.
Эти изменения следуют после технической проверки утверждённого правила и испытаний
на копии. Действующие защиты не отключены; внедрение требует отдельного разрешения.

## Оставшиеся технические подтверждения

Правило отсутствия/возвращения и запрет запасного старого остатка уже утверждены;
повторно спрашивать владельца о них не нужно. Для внедрения остаётся установить:

1. Какими доказательствами подтверждается полный статус именно данного канала
   и конкретной версии файлов: контракт поставщика, контрольные записи/итоги,
   согласованность пары, SHA и привязка к принятому snapshot. Одной CRC недостаточно.
2. Полную последнюю принятую пару snapshot №8 для точного рабочего списка absent,
   включая складской карантин, protected supplier-строки и фактическую выбранную цену.
3. На восстановленной копии: корректное обнуление/исключение только своих складов,
   автоматическое возвращение по новым данным и отсутствие старого stock fallback;
   отдельно прежнюю каноническую работу цены другого источника без смены приоритетов.
4. Корректный безопасный отказ неполного набора, rollback и сохранение manual/locked.

Это технические условия испытания, а не повторное согласование принятого правила.
Дополнительные новые бизнес-лимиты не вводятся. Вопросы вне этого уточнения
(например, режим цен/витрины при длительной недоступности FTP) не подменять
самостоятельно выбранными значениями.

Следующий этап — получить технические подтверждения, интегрировать правило в прежний store/reader и
транзакцию публикации, испытать на восстановленной копии и показать результаты.
