# PRICAT v2: изолированная интеграционная проверка

Уточнение владельца от 17.11.2026, [issue #4](https://github.com/stron111-web/elektrikamarket/issues/4#issuecomment-6953675526), отменяет остановку испытаний из-за отсутствия отдельного письма поставщика. После технической проверки актуального источника отсутствие кода означает ноль доступного supplier-остатка только для его складов: PRICAT1 — stock1/stock3, PRICAT2 — stock2. Возвращение использует новую запись. PRODAT не удаляется. Уменьшение количества строк само по себе не ошибка.

## Код и границы

- `scripts/pricat-update/reviewed-import.cjs` — явный путь проверки пары: ZIP/CRC/XML, стабильный SHA, ожидаемые SenderGln/DocumentNumber/Currency, непротиворечивые статистики; затем существующий `importPricat` с карантином и атомарным снимком. Политика называется `owner-current-source-v2`. Новых процентных veto нет.
- `reviewed-import.test.cjs` проверяет техническую привязку и отсутствие fallback БД без обращения к PostgreSQL.
- `integration-fixture.cjs` — намеренно привязан к существующей восстановленной БД `pricat_restore_20261117t152456z`. Не создаёт БД, не загружает dotenv и production-конфигурацию. Допускает только loopback и отсутствие внешних маршрутов. Запускатель отдельно проверяет ID контейнера и единственный отдельный том.
- `integration-edgecases.cjs` — контрольные изменения отдельных записей реального полного XML. Такие файлы явно помечены как синтетические и не являются новыми выгрузками поставщика.
- `scripts/import/pricat-zip.cjs` — ограниченный по объёму поток ZIP-entry через стандартные fs/zlib/pipeline с проверками заголовка, CRC и размера. Центральный каталог читает существующий unzipper, SAX/XML и нормализация сохранены. PRICAT2 XML и импорт PRODAT не меняются.
- `integration-zip-regression.cjs` проверяет полный реальный ZIP с асинхронным потребителем без SQL.

Установленные на VPS `update.cjs`, cron и production-конфигурация **не подключены** к новому модулю. Это испытательный интеграционный путь, не готовый production-релиз. Нельзя выдавать прохождение unit-тестов за результат записи на копии.

## Набор испытаний

Использовать сохранённые пары за 5 и 6 ноября последовательно, сверять реальные изменения цен/остатков и исчезнувшие коды. Сравнивать полные контрольные отпечатки мастер-таблиц. Повтор неизменённой пары должен дать SKIPPED без изменения активного снимка. Инъекция ошибки перед активацией снимка должна откатывать коммерческие данные, оставляя прежний снимок видимым независимому читателю.

Контрольные случаи на существующих товарах копии: конфликтующие дубли, отрицательное количество, защищённая цена при смене UOM/упаковки, отсутствие кода и пустое количество, защищённый supplier-остаток, ручная цена, защитная наценка и NMP без деления цены/количества. Сценарии дополнены отсутствием кода в PRICAT2, карантином только stock3 при неверной PartnerUOM и отдельным откатом действительно изменённых значений. После испытания вернуть исходную пару и снять только созданные тестом флаги/строки. Технически повреждённые файлы должны отклоняться до коммерческой записи.

Оба интеграционных скрипта создают доказательства в `/results`. Тестовый процесс ограничен CPU/RAM, запускается без Docker socket, production-томов, секретов и внешней сети. Контроль отсутствия прогресса через 300 секунд завершает только тестовый процесс; разрыв соединения откатывает его открытую транзакцию. Это защита испытания, не установленный production watchdog.

Повторять начальный скрипт поверх уже созданной схемы `pricat_v2_test_20261117` нельзя: он намеренно останавливается на существующей схеме. Не выполнять автоматические DROP/restore ради повторного запуска. Для продолжения после ошибки сначала определить фактический этап по журналу.

В испытании обнаружены ошибки самого проверяющего скрипта (формат loopback inet `/32`, регистр SQL-alias) и остановка прогресса старого ZIP-потока на 85 199-й строке при асинхронной записи spool. Контроль прогресса завершил только тестовый процесс с кодом 124; коммерческая публикация следующей пары не началась. Добавлено явное `--resume-after-nov5`: сверяются принятые SHA, снимок 9, исходные мастер-отпечатки и полное сохранённое коммерческое состояние; первая пара не публикуется повторно. Старый незавершённый тестовый аудит обрабатывается штатным механизмом импортёра.

Точное внутреннее место блокировки прежнего процесса не установлено: после таймаута его runtime-стек уже недоступен. Обход custom ZIP PullStream проверяется реальным полным асинхронным прогоном и последующими публикациями; нельзя заявлять, что причина исторического зависания production доказана по одному совпадению симптомов.

## До отдельного согласования развёртывания

Нужны фактический отчёт интеграционных запусков, проверка обнаруженных дефектов, обновление документации и коммит. Далее — проект включения v2 в существующий запускатель с сохранением блокировки, metadata-skip, повторной обработки, атомарности, ручных данных и согласованности источников. Production-бэкап/откат и watchdog проверяются отдельным планом. Не переносить в production фиксированный тестовый DSN, тестовые XML, искусственные защиты и аудит-схему.

## Продолжение после согласованной ночной паузы

17 ноября по просьбе владельца заморожены только helper контрольных сценариев и его отдельная PostgreSQL. Перед продолжением 18 ноября проверены точные ID и изоляция. Helper снят с паузы при ещё замороженной БД: собственный таймаут завершил его с 124 без SIGKILL. Затем возобновлена только тестовая БД; снимок 10/131544 и отсутствие оставшихся соединений проверены запросом чтения.

`integration-edgecases.cjs --resume-controls` не повторяет подбор/создание тестовых данных. Он требует прежнего успешного контрольного rollback, исходного снимка и точного совпадения всех коммерческих строк с checkpoint с учётом только двух тестовых locked-цен, одного locked-остатка и собственной MANUAL-строки. Он использует уже созданные synthetic XML с прежними SHA. При несовпадении останавливается до повторной публикации. Бизнес-состояние не восстанавливается произвольным SQL.

При первом продолжении обнаружено различие представления bigint (`"10"` вместо `10`) в проверяющем коде. Проверка остановилась до записи; сравнение исправлено. Ошибочный промежуточный JSON отчёта сохранён, история событий восстановлена из сохранённого полного журнала. Это дефект harness, а не отказ новой торговой политики.
