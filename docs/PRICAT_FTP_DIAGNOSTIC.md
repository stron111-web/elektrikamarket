# Диагностика FTP 530 и исправление скрытого ввода

Дата: 01.11.2026, Europe/Astrakhan. Ветка codex/pricat-ftp-russvet.
Реальные логины, пароли, XML/JSON секретов и HMAC в этот отчёт не включены.

## Установленная причина

С VPS выполнена ровно одна диагностическая попытка авторизации:

| Этап | Ответ |
|---|---|
| TCP/connect, FTP greeting | 220 |
| USER | 331 |
| PASS | 530 |

530 возвращается именно после PASS. Команды PASV/EPSV, LIST/MLSD, RETR,
ACCT и импорт не выполнялись. Ответ классифицирован как общий отказ входа;
детальный ответ сервера и аргументы USER/PASS не логировались.

Приватное сравнение со всеми двумя записями FileZilla для service.russvet.ru:21021
показало: и логин, и пароль в файле VPS **не совпадают** с сохранёнными в FileZilla.
Сравнивались HMAC с одноразовым случайным ключом в памяти, в отчёт/логи попали
только результаты равенства. Сами контрольные значения не сохранялись.

В обоих полях VPS вместо текста обнаружен управляющий ввод Ctrl+V, без
содержимого вставляемого текста. Это подтверждает сбой скрытого консольного
ввода: клавиша вставки была принята как данные. Удалением управляющих символов
реквизиты не восстановить — действительного текста в этих полях нет.

Ошибка нашей обвязки: Read-Host -AsSecureString оказался неподходящим для такой
вставки в текущем терминале; sender/receiver/client проверяли лишь CR/LF/NUL и
пропустили другой ASCII control. Предыдущее заключение «формат корректен» было
слишком слабой проверкой. Реальные значения владельца при этой диагностике не
редактировались, неизвестный пароль не угадывался.

## Что исключено

- Audit обёртки socket.sendall подтвердил: USER и PASS ушли точно в UTF-8 байтах
  строк сохранённого JSON. Ни экранирование JSON, ни SSH, ни ftplib не меняли их.
- Сохранённые строки ASCII, без пробелов по краям. Невидимые controls, а не разная
  кодировка UTF-8/CP1251, объясняют конкретный отказ.
- DNS Windows и фактический TCP peer VPS совпали: 91.208.126.4.
- Пассивный/активный data channel не может объяснить этот экземпляр 530: до его
  открытия дело не дошло. Нет свидетельств IP-блокировки; наличие ограничений
  поставщика вообще не проверяется этим тестом, но для отказа уже найдена причина.

## Сравнение параметров

| Параметр | FileZilla, сохранённые настройки | VPS, фактическая попытка |
|---|---|---|
| Host/port | service.russvet.ru:21021 | service.russvet.ru:21021 |
| Protocol | Protocol=0 (FTP); сервер не поддерживает AUTH TLS/SSL по предыдущему probe | Обычный FTP, TLS выключен явно |
| Encoding | UTF-8 | UTF-8 |
| Login | Logontype=1, сохранённая пара | USER → PASS; другая фактическая пара из повреждённого ввода |
| Proxy | FTP Proxy type=0, Proxy type=0 | Не используется |
| Data mode | MODE_DEFAULT | Passive; на этапе отказа ещё не используется |

Это сравнение конфигурации, а не новая успешная Windows-авторизация: повторных
попыток входа с Windows или вариантов пароля не делали.

## Исправлено

1. Windows sender использует Get-Credential в Windows PowerShell 5.1 — штатный
   диалог вместо скрытого консольного Read-Host. Registry/ExecutionPolicy не меняет.
   Если включён ConsolePrompting, останавливается, не откатываясь на прежний ввод.
2. Отправитель, Python receiver и Node FTP client отвергают все ASCII C0/DEL
   до сохранения/подключения. Ничего автоматически не обрезают/нормализуют.
3. SecureString конвертируется с явной длиной, чтобы встроенный NUL не мог
   незаметно обрезать пароль перед проверкой. Unicode/пунктуация сохраняются.
4. Исправленный receive-credentials-v2.py подготовлен отдельным файлом на VPS,
   с SHA-256/проверкой синтаксиса/0600. Старый receiver и файл реквизитов сохранены.
5. Параметр sender -ReplaceInvalid — только явное действие владельца: после
   корректного нового ввода сохраняет private backup исходного ошибочного файла,
   затем устанавливает новый файл через stdin SSH. Архивация разрешена только
   для доказанного Ctrl+V-only дефекта в обоих полях; корректный/другой файл,
   публичные права или symlink она не заменяет. Это не общий reset/rotation.

Get-Credential/диалог Windows 5.1: [документация Microsoft](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/get-credential?view=powershell-5.1).
Действительный текст владельцу нужно ввести заново: он не может быть восстановлен
из управляющих символов. Ничего не копируется из FileZilla автоматически.

## Проверено фактически после исправления

- Node regression: **127 tests, 126 passed, 0 failed, 1 skipped**, ~5.40 с,
  только новый локальный Docker PostgreSQL; fixture удалена с проверкой меток.
  Контрольные символы в двух полях отклонены до создания сетевого соединения.
- Python receiver: **7/7 PASS**, включая 66 вариантов control-полей, UTF-8/кавычки,
  отказ перезаписи/symlink/публичных прав, сохранность invalid backup и отказ
  архивации исправного файла.
- Windows PowerShell 5.1: фактическая функция формирования JSON прошла
  **5 точных UTF-8 round-trip** (включая Unicode, emoji, кавычки, slash, $/backtick,
  пробелы) и **66 отказов для control**. GUI с реальными данными не открывался.
- Реальное соединение с новыми корректными данными ещё не проверялось: требуется
  повторный ввод владельцем. Текущий секретный файл VPS не исправлялся автоматически.

Полный TAP/stdout/stderr вне Git: validated-em-pricat-regression-e3b6784f681c.
БД, коммерческий снимок, импорт, расписание, сайты и FileZilla-конфигурация не менялись.
Push/merge не выполнялись.

## Действие владельца

Вставить в PowerShell (публичные пути в команде, никаких значений реквизитов):

```powershell
powershell.exe -NoProfile -Command "& ([ScriptBlock]::Create([IO.File]::ReadAllText('C:\projects\elektrikamarket\backups\pricat-ftp-russvet\deploy\pricat\send-ftp-credentials.ps1'))) -ProjectRoot 'C:\projects\elektrikamarket\backups\pricat-ftp-russvet' -ReplaceInvalid"
```

Откроется отдельный штатный диалог Windows. В нём вставить корректную пару из
FileZilla; пароль скрыт. Отмена/невалидный новый ввод не меняет существующий файл.
После успешной отправки сообщить только «реквизиты переданы повторно».
Команда сама не выполняет FTP-вход/скачивание, импорт или включение расписания.
