# Готовый ассортимент после PRICAT

Статус: реализация в ветке `codex/assortment-snapshot`, база main `6540963`.
Развёртывание, миграции/импорты на рабочей или сохраняемой VPS БД **не выполнялись**.
Актуальное основание — [Issue №1](https://github.com/stron111-web/elektrikamarket/issues/1),
включая дополнения владельца от 29.10 и контракт корзины/API.

## Минимальная структура

Добавлены ровно две таблицы:

- `assortment_snapshots`: дата, версия SQL-проекции, ссылки на успешные PRICAT1/2,
  источник запуска, защитная наценка, количество позиций и признак active.
- `assortment_items`: PK (snapshotId, productId), выбранный источник, базовая
  розничная цена, закупочная Price2, единица продажи, упаковка/кратность и JSONB
  массива допустимых складов. Складов максимум три: отдельная таблица для них не нужна.

Один partial UNIQUE index допускает не более одного active snapshot.
PK индексирует выборку поколения и lookup товара. Product связан FK;
названия, категории, бренды, изображения/документы/характеристики не копируются.
Фильтры используют существующие индексы Product.categoryId/brandId; поиск сохраняет
исходный параметризованный ILIKE и буквальное экранирование %, _ и backslash.
Никаких новых extension, Redis, очередей, фоновых процессов, revision-триггеров,
редактора ручных цен или инфраструктуры для будущих пользовательских правок нет.

Stocks хранятся как JSONB с quantity **строкой Decimal**, не JavaScript float.
Розничная цена — защищённая базовая цена продажи обычному клиенту; не персональная.
Закупочная цена взята из **того же коммерческого источника**, что выбранная розничная.
Для существующего корректного MANUAL без Price2 сохраняется NULL; это не повод
отменять действующий приоритет ручной цены или придумывать закупку.

## Единые торговые правила

`availableStocksQuery` в pricat-store.cjs компонует существующий readAvailableStocks
с SQL-множеством товаров. Это перенесённый helper из web/lib/availability.cjs;
сами функции выбора цены/доступности и условия не менялись.

Builder материализует эту общую проекцию один раз и агрегирует допустимые склады.
Упаковка и Price2 присоединяются по уникальному контексту Product + priceSource.
Нет независимой второй реализации правил MANUAL → PRICAT2 → PRICAT1,
защитной наценки, UOM, NMP и карантина. Проверяются структурная целостность,
положительные количества, совместимость UOM и уникальность складов.

Недопустимые цены, отсутствие положительного допустимого остатка, архив и
блокирующие конфликты отбрасываются самой исходной проекцией. Locked/manual
сохраняются прежним импортёром, включая поведение карантина supplier-stock.
Отсутствие количества не становится нулём; содержимое упаковки не умножает QTY.

## Публикация и ошибки

1. Импортёр читает/проверяет оба явно переданных PRICAT штатным способом.
2. В существующей транзакции публикуются source-данные и итоговые статусы файлов/run.
3. После SUCCEEDED-статусов строится отдельное неактивное поколение. Это важно:
   общая проекция видит только успешный аудит, включая новый карантин.
4. После структурных проверок прежний active становится false, новый — true.
5. Source и snapshot фиксируются **одним COMMIT**; readers используют обычный MVCC.
   Между двумя UPDATE публичный reader не видит промежуточный пустой каталог.

При любой ошибке до commit новые source writes/статусы/поколение откатываются;
действует предыдущий полный snapshot. Ошибка расчёта не маскируется публикацией
частичного результата. Законный результат «0 допустимых товаров» может публиковаться.

Используется прежний advisory key PRICAT, без нового сервиса блокировок.
Builder выполняется в той же публикационной транзакции и использует source table
locks, совместимые с обычным чтением. Хранятся активное и одно предыдущее поколение;
старые производные строки удаляются только внутри транзакции новой публикации,
CASCADE ограничен snapshot → items. Source-товары и аудит не удаляются.

Обычный запуск только одного PRICAT обновляет его source-данные по прежним правилам,
но **не публикует новый снимок**. Для штатного цикла нужно передать оба источника
одним вызовом. Прежняя snapshot-выдача сохраняется. Повтор той же успешно обработанной
пары не перестраивает поколение, если provenance, версия и protective markup совпали.
Версия проекции требует повышения при будущем изменении торгового SQL.

## Чтение и актуальность

Покупательский каталог/карточка используют готовые retailPrice, stocks и упаковку,
без обращения к price/stock/quarantine predicates на каждом HTTP-запросе.
Закупочная цена не входит в публичный DTO и HTML. Для snapshot-таблицы web получает
только column SELECT, исключающий purchasePrice.

Count и страница читаются в одной REPEATABLE READ READ ONLY транзакции,
generation_id закреплён на весь запрос. Точный count выполняется по компактному
готовому множеству с join к Product, не пересчитывает торговлю. Размер страницы 24,
ORDER BY Product.id, clamp последней страницы и категории с потомками сохранены.
Данные PRODAT читаются из исходных таблиц. Архивный Product дополнительно скрывается.

У недоступной карточки сохраняется прежний контент, но нет продаваемого оффера:
«Нет доступного предложения». Не назначаем самостоятельно новую политику HTTP 404
для существующего товара. Фиктивная/несуществующая карточка по-прежнему 404.

`STOREFRONT_DIAGNOSTICS=1` разрешает «Все товары» только на явно диагностическом
стенде; default 0 скрывает переключатель и игнорирует попытку `availability=all`.
Этот режим показывает полный каталог PRODAT, но офферы — из опубликованного снимка.
Это не новая админка и не система разграничения ролей: флаг нельзя включать на
открытой покупательской витрине. Existing Basic Auth тестового стенда сохраняется.

Снимок сознательно фиксирует коммерческие данные до следующего парного обновления
или явно разрешённого rebuild. По последнему решению владельца немедленная
инвалидация ради гипотетических ручных правок исключена. MANUAL/locked уже
существующей БД учитываются **при построении**. Смена защитной наценки отражается
следующим rebuild; редактора настроек и наблюдателей за произвольным SQL нет.
Персональные наценки/скидки — будущий отдельный слой, они не перестраивают этот снимок.

Если активного совместимого поколения нет, reader завершается ошибкой подготовки,
а не выдаёт пустой каталог или тайно запускает старый тяжёлый расчёт.
Bootstrap обязателен **до** переключения на новый образ.

## Bootstrap и будущий релиз — только по отдельному разрешению

При будущем внедрении: резервная копия → новая additive migration → служебный
bootstrap → сравнение → адресный snapshot-grants.sql → новый web image → проверки.
Не использовать init/reset/import для создания первого снимка из существующей БД.

Одноразовый CLI (URL заранее загружен защищённо в указанную переменную):
`node scripts/storefront/rebuild-assortment.cjs --database-url-env SNAPSHOT_TARGET_URL`.
Он не читает .env автоматически, не запускает миграции и не получает пароль аргументом.
Проверяет наличие обоих успешных источников, использует транзакцию, advisory lock,
statement_timeout 60s и lock_timeout 2s. Не запускать на VPS в рамках этой задачи.
Имя базы/переменной не является разрешением на операцию.

Migration и GRANT-файлы пока только подготовлены. Роль storefront_test_ro остаётся
read-only; строитель работает отдельным явно разрешённым соединением.
Caddy/HTTPS, SSH и публикация портов не меняются.

Ошибка публикации уже откатывается транзакцией. Для отката приложения можно вернуть
прежний образ (аддитивные таблицы оставить): старый reader снова использует канонический
расчёт текущей БД. Не восстанавливать старые товары/цены ради отката UI и не выполнять
down -v. Слепой ручной выбор старого поколения после новых данных не автоматизирован.

## Проверки и измерения

`npm run test:assortment` использует только явный ASSORTMENT_TEST_ADMIN_URL;
без него DB-suite пропускается и не подхватывает рабочий DATABASE_URL.

Полный сценарий:
`node scripts/storefront/check-local.cjs <private-database.dump> [image]`.
Проверяет SHA-256, создаёт новую локальную сеть/volume/PostgreSQL, случайные fixture БД,
применяет миграции только туда, затем восстанавливает отдельную копию архива.
На восстановленной копии выполняется ANALYZE: dump не переносит статистику planner.
Это не подключение к рабочей БД и не анализ VPS.

Тесты проверяют старые импорты, полную эквивалентность офферов на копии через
двусторонний EXCEPT ALL, закупочные цены и упаковки, MANUAL/locked, карантин,
ошибку перед активацией, видимость незакоммиченного поколения, старого RR-reader,
пустой корректный snapshot, права, категории/фильтры/пагинацию и HTTP HTML.
Benchmark получает старый reader через git show 6540963, а не дублирует правила
в production-коде. Сравниваются оба механизма на одном наборе данных и машине.
Созданные ресурсы адресно удаляются в finally; существующие контейнеры не меняются.

Исторический deploy/storefront/check-local.cjs перенаправляет на этот сценарий.
Текущий прогон не повторяет проверку публичного ACME-сертификата или VPS-логинов.
Полный PRODAT_FULL_TEST с исходными ZIP — отдельный opt-in, он не нужен для этой задачи.

## Фактический локальный прогон 30.10.2026

Production Docker build (Node 24 / Next.js 16, включая TypeScript) и Prisma validate
прошли. Суммарно 98 тестов: 97 PASS, 0 FAIL, 1 SKIP — opt-in полный PRODAT
с исходным ZIP поставщика. HTTP smoke выполнен через настоящий production image
и роль storefront_test_ro, включая запрет чтения purchasePrice и записи.

Архив проверен по SHA-256 и восстановлен только в новый временный Docker volume.
Построено 125 082 оффера за 6 117 мс. Полное двустороннее EXCEPT ALL:
missing=0, extra=0; расхождения закупочных цен/упаковок=0. Проверенные source
таблицы сохранили количество строк. Fixtures и их том/сеть удалены после теста.

Измерения двух последовательных обращений, миллисекунды (старый → snapshot):

| Запрос | Старый 1 / 2 | Snapshot 1 / 2 |
|---|---:|---:|
| Каталог | 3951 / 3935 | 145 / 133 |
| Страница 2 | 3736 / 3978 | 129 / 135 |

Это локальная копия с ANALYZE, последовательные вызовы без нагрузки; не замер VPS,
не SLA и не гарантированно холодный cache. Замер включает SQL reader/count/page/DTO,
не внешние изображения, HTTPS или полное время браузера. Основной каталог ускорился
примерно в 27–30 раз; поиск по коду не ускоряется во всех случаях. Существующий
ILIKE по названию/артикулу остаётся ограничением; отдельный поисковый индекс/механизм
не добавлялся. Категории и бренды берутся из PRODAT без копирования в snapshot.

Перед будущим релизом нужны отдельное разрешение на миграцию/bootstrap/GRANT и
проверка на целевой среде. Старый образ можно вернуть без удаления новых таблиц.
