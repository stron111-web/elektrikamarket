# Подготовка релиза PRICAT v2, 18 ноября 2026

Фактическое ограниченное внедрение описано отдельно в
[отчёте от 18.11.2026](PRICAT_V2_PRODUCTION_20261118.md).
Ниже сохранён исторический план подготовки, а не текущее состояние VPS.

Документ не разрешает установку, публикацию, удаление данных или смену cron.
Рабочий режим остаётся `check`, PRICAT раз в 3 часа, PRODAT раз в 12 часов.

## Состав

`sourcePolicyVersion=owner-current-source-v2` явно выбирает проверенную политику.
Прежние процентные ограничения не участвуют в ней. Старый режим оставлен для
обратной совместимости; наличие нового кода само по себе не переключает рабочую БД.
Канонический `pricat-store.cjs` не меняется. Нет второго механизма цен или остатков.
Неидентифицируемый код/неправильный документ/повреждение блокируют публикацию;
идентифицируемые ошибки и конфликтующие дубли изолируют соответствующий код источника.

Используется нативный ограниченный ZIP-поток с CRC/size, отменой и закрытием
декомпрессора. Старый зависавший путь `entry.stream()` не используется в проверке
и импорте PRICAT. Worker считает прогресс по изменению фаз/счётчиков, а не heartbeat.
Технические лимиты: 90 минут на запуск, 15 минут без прогресса, 15 секунд на отмену;
SQL statement/idle-in-transaction — 5 минут. Это не ограничения изменения ассортимента.
Host supervisor сохраняет логи до удаления собственного завершившегося контейнера.
При неподтверждённом завершении оставляет `needs-review`, не применяет SIGKILL.
Независимый наблюдатель уведомлений описан в `deploy/import-monitor/README.md`.

## FTP_SOURCE_DATE

18.11.2026 в 06:12:03.465 UTC PRICAT2 с именем
`PRICAT_891661_2630_20261118063515.xml` был отвергнут как будущий:
имя трактовалось как 06:35:15 UTC. Полученный FTP MDTM: 03:37:00 UTC.
Нельзя надёжно назначить часовой пояс строке имени; MDTM уже определён как UTC.
Новая проверка возраста использует MDTM; календарная валидность имени,
точное соответствие XML/имени, SHA и монотонность документов сохраняются.
Порог будущего времени не увеличивается. Для локального манифеста без MDTM
старое поведение остаётся явным резервным вариантом.

Неизменившиеся имя/SIZE/MDTM последней **успешно принятой** версии дают ранний
`NO_REMOTE_CHANGE`, до чтения кеша, выделения staging и создания runs.
Изменившийся источник скачивается один; неизменённый второй берётся из принятого
кеша с проверкой SHA. Пара повторно сверяется после скачивания.
`reprocess=true` использует принятую пару без FTP и обходит SHA-skip.
После успешного запуска очищаются только его собственные копии ZIP/XML;
два последних принятых файла каждого источника сохраняются. Исторические runs
этим релизом не очищаются. Кеш последней принятой пары не удалять.

## Почему 137359 и 131544

Рабочий снимок №8 основан на прежних принятых источниках; испытательные снимки
используют реальные выгрузки 5/6 ноября. Сравнение по productId:

| Изменение | Товаров |
|---|---:|
| Исходные предложения | 137359 |
| Исключены | 6504 |
| Добавлены | 689 |
| Итог | 131544 |

6486 исключённых кодов отсутствуют в обеих новых выгрузках, остатки обнулены.
Ещё 18 имеют корректную цену, но единица положительного остатка отличается от
единицы продажи: канонический `readAvailableStocks` возвращает для них ноль ячеек.
Это не удаление товаров PRODAT; основной каталог из 180666 товаров сохранён.
Данные исторических пар не являются прогнозом свежей выгрузки на день установки.

## Установка после отдельного разрешения

1. Проверить состояние рабочей БД, активный снимок, принятые SHA, актуальные FTP
   метаданные, маркеры, lock, процессы, свободное место и здоровье двух сайтов.
   Сохранить crontab, runtime.env, config.json и immutable IDs обоих импортёров
   в закрытой папке отката. Не выводить конфигурацию или содержимое секретов.
2. Под общей блокировкой создать **новый** согласованный pg_dump рабочей БД.
   Проверить SHA, `pg_restore --list`, восстановить в согласованную существующую
   изолированную среду после сохранения результатов её испытаний. Не запускать
   старый `backup-rehearse.py`: он создаёт ещё один большой volume.
   Сверить таблицы/последовательности и ключевые количества. При сбое остановиться.
3. Подготовить отдельный config командой из корня проверенного релиза:

   ```sh
   python3 deploy/pricat/prepare-config.py --input /home/shopadmin/elektrikamarket-pricat/runtime/config.json --output /home/shopadmin/elektrikamarket-pricat-v2-release-20261118/runtime-candidate.json
   ```

   Она не перезаписывает live или существующий output, сохраняет адреса и ссылки
   на защищённые реквизиты, убирает старые процентные поля и задаёт явную v2.
   Сверить кандидат локально на VPS без вывода секретов.
4. Установить подготовленный host supervisor/наблюдатель обычными правами shopadmin
   и стандартным sudo для systemd, как описано в его README. Ввести SMTP-пароль
   скрыто и отдельно согласовать испытательные письма. До этого `mailEnabled=false`.
5. Под блокировкой заменить только существующие файлы запускателя/конфига/ссылку
   на проверенный immutable image. Не пересоздавать PostgreSQL, сайты или Caddy.
   Предварительно убедиться, что PRODAT использует совместимый образ, его runtimeLimits
   заданы и вся цепочка повторного сопоставления испытана; старый PRODAT нельзя
   объявлять защищённым новым ZIP/worker только из-за обновления PRICAT.
6. Сначала `check`. После отдельного разрешения — один контролируемый `publish`
   под прежней общей блокировкой. Сверить исходники, снимок, ассортимент, цены,
   остатки по складам, карантин, ручные поля, отсутствие зависшей транзакции.
   Успешное обновление принятого FTP-state обязательно. Не повторять вслепую.
7. Автоматический `publish` включать только по разрешению после успешного рабочего
   запуска: заменить режим в тех же двух строках cron, не создавать дубликаты.
   Сохранить UTC `12 */3 * * *` и `0 11,23 * * *` (PRODAT 15:00/03:00 Самара).

Откат кода: под блокировкой вернуть сохранённые конфиг/образ/запускатели и `check`.
Это не откат данных. Восстановление поверх рабочей БД отдельно запрещено без согласия.
Не удалять неопределённые маркеры, lock или контейнеры при неподтверждённом COMMIT.

## Диск и очистка — только предложение

Сохранить рабочий `elektrikamarket-deploy_pgdata`, текущий изолированный recovery-том
и последнюю старую копию `elektrikamarket-prodat-rehearsal-20261105t120511z-data`.
У остальных шести старых томов контейнеры остановлены, в проверенных действующих
скриптах ссылок не найдено. Их удаление требует отдельного согласия и предварительной
архивации нужной диагностики. Не выполнять `docker system prune` или volume prune.

Не удалять `state/ftp/versions` принятой пары, диагностические файлы ошибок и
исходники незавершённого запуска. Старые успешные ZIP/XML из `state/runs` можно
убирать только по отдельному манифесту после проверки SHA, статуса и наличия принятой
пары/бэкапа. `issues.ndjson` — диагностика, не исходник; для него отдельный срок хранения.
Новая очистка относится исключительно к своим будущим подтверждённым runs.
