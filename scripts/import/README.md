# PRODAT: потоковый разбор, dry-run и production

Запуск из корня проекта на Node.js 24 (или через установленный tsx):

    node scripts/import/prodat-dry-run.ts
    node scripts/import/prodat-dry-run.ts path/to/PRODAT_file.zip
    node --test scripts/import/prodat.test.cjs

Без аргументов обрабатываются два исходных PRODAT ZIP. PostgreSQL не используется.

Общий модуль prodat.cjs экспортирует асинхронные генераторы parseProdatXml и readProdatZip. Production-импортёр prodat-import.cjs использует эти же генераторы. Каждый результат содержит record и позицию; ZIP-обёртка добавляет источник. Потребитель может ожидать асинхронную обработку каждой записи. Дерево всего документа не накапливается: удерживаются текущая запись, ограниченный чанк и результаты этого чанка. Память дедупликации растёт с количеством уникальных кодов, но хранит только SHA-256 и источник первой записи.

Формат: текстовый лист — строка без автоматического преобразования чисел; пустой элемент — пустая строка; вложенные элементы — объект; повторяющиеся одноимённые элементы — массив в исходном порядке; атрибуты — @attributes; текст объекта — #text. Для смешанного содержимого #content сохраняет порядок текста и дочерних элементов. Пробелы текстовых листьев сохраняются; отступы между вложенными элементами игнорируются. Комментарии и processing instructions не являются полями товара.

Кодировка определяется по BOM и XML declaration (заголовок до 4096 байт). Поддерживаются UTF-8, UTF-16LE/BE и Windows-1251. Без указания используется UTF-8. Противоречия, неподдерживаемая кодировка, некорректный XML и DTD вызывают ошибку. Декодер сохраняет состояние между чанками. Запись — только прямой DocDetail внутри Document.

Дедупликация: SenderPrdCode обязателен и должен быть однозначным. Каноническое представление сортирует ключи объектов, сохраняя порядок массивов и значения текста. Совпавший SHA-256 означает идентичный дубль и пропуск. Отличие от первой записи — конфликт: выводятся оба источника и хеша, dry-run завершается с ненулевым кодом. Первая запись не заменяется; при конфликте будущий writer не должен считать загрузку успешно завершённой. Хеши не заменяют хранение конфликтующих исходных данных в будущей системе аудита.

Для исходных архивов ожидаются rawRecords=148882, uniqueSenderPrdCode=148872, identicalDuplicates=10, conflicts=0. Dry-run также выводит вложенные поля товара 1804651. ZIP исключены из Git правилом PRODAT_*.zip.

## Production importer v1.2

Реализованы `ImportRun`, `ImportFile`, `ImportIssue`, `Brand`, `Category`, `Product`,
`ProductBarcode`. `ProductFeature`, `ProductImage`, `ProductDocument`,
`ProductRelation`, цены и остатки не записываются. `Multiplicity` относится к
коммерческим данным и в этом этапе не переносится.

Запуск требует явно указать переменную окружения с PostgreSQL URL и все ZIP-части
одного логического каталога. Не передавайте пароль непосредственно в командной строке.
Пример для заранее подготовленной тестовой БД:

    node scripts/import/prodat-import.cjs --database-url-env PRODAT_TEST_URL path/to/part1.zip path/to/part2.zip

Без аргументов записи не будет. `.env` читается только CLI; библиотечный вызов
`importProdat({ databaseUrl, files, batchSize: 500, onProgress })` требует URL явно.
`onProgress` — синхронный callback; его ошибка отменяет текущий запуск.
Поддерживается только PostgreSQL/public. Используются установленные `postgres`,
`dotenv`, `unzipper`, `sax`, `iconv-lite`; Prisma Client generation не требуется.
`postgres` и `dotenv` сейчас доступны через существующее дерево зависимостей
(как и в `init-system-data.ts`); перед отдельной упаковкой импортёра их следует
объявить прямыми зависимостями. В рамках этой задачи package.json не изменяется.

### Публикация и повторный запуск

1. Сессионная advisory-блокировка исключает одновременные PRODAT writer-процессы.
2. Создаются RUNNING ImportRun/ImportFile, сохраняются SHA-256, размер и путь ZIP.
3. Общий streaming parser проверяет все XML всех ZIP, включая ранее успешные SHA.
   Полная исходная запись участвует в сравнении дублей, включая пока не
   импортируемые вложенные поля. Сравнение консервативное: порядок ключей объектов
   не важен, порядок массивов и исходный текст важны; разные данные не объединяются.
4. `prodat-normalize.cjs` проверяет и нормализует данные. Пакеты до 500 уникальных
   новых записей сохраняются в PostgreSQL TEMP-таблицу. В JS остаются пакет, карта
   хешей/источников и узлы категорий; весь XML не накапливается.
5. Перед публикацией SHA проверяется повторно. Каталог и успешные статусы аудита
   фиксируются одной транзакцией. Табличные блокировки защищают публикацию от
   параллельных изменений каталога. Ошибка откатывает весь каталог, FAILED-аудит
   записывается отдельно. Исходные архивы нужно сохранять по указанным путям.
6. При повторном запуске SHA, успешно обработанный всеми текущими слоями, получает
   SKIPPED и не публикуется вновь,
   даже под другим именем. Он всё равно проверяется на конфликт с другими частями.
   Свежий SHA с неизменными нормализованными значениями не обновляет Product,
   включая timestamps и provenance. Отсутствующие товары не затрагиваются.

После аварийного завершения незавершённый RUNNING этого importerVersion переводится
в FAILED при следующем запуске под эксклюзивной advisory-блокировкой. Затем исходный
набор можно импортировать повторно. Если связь с БД потеряна, немедленное сохранение
FAILED может быть невозможно; CLI показывает `auditError`. Потерянный ответ COMMIT
не должен переименовывать уже зафиксированный SUCCEEDED в FAILED. Автоматического
продолжения посередине файла нет: повторно проверяется весь набор.

### Правила нормализации

- `SenderPrdCode` → уникальный `supplierCode`; обязательны код и ProductName.
- Brand identity — название после trim/NFC, с сохранением регистра. Имена не
  объединяются по догадкам или транслитерации.
- Category identity — `rsv:catalog:L4:id`, `L3:id`, `L2:id`; дерево L4 → L3 → L2.
  При пропуске уровня используется ближайший доступный предок. Товар без RsCatalog
  получает `categoryId=null` (требует категоризации); ETIM остаётся полями Product.
  Противоречивые имена/родители одного sourceKey в одном наборе — ошибка.
- Новые slug строятся из name общим prodat-slug.cjs. Коллизии разрешаются стабильным
  суффиксом identity; существующие slug не меняются, в том числе после переименования.
  Технические slug старого v1.0.0 исправляются только отдельным одноразовым repair.
- Countries: один/несколько Country.Value → trim/NFC, удаление пустых значений,
  уникальность, сортировка. Сохраняются названия поставщика, без угадывания ISO-кодов
  и синонимов. GOST/TY объединяются из DocDetail и CertificateInfo.
- LabelledItemCHZ: только `Y`, `N`, `check`, `null`; неизвестное значение — ошибка.
- Decimal(20,10): строка → точная десятичная строка → PostgreSQL numeric, без Number.
  Поддержаны `1.`, `0.`, `.5`; превышение точности и экспоненциальная запись отклоняются.
  Исходные Weight/Dimension/ItemsPerUnit сохраняются в physicalRaw, нули не исчезают.
- `lockedFields` содержит точные имена полей модели: например `name`, `brandId`,
  `categoryId`, `countries`, `weight`, `parentId`. Заблокированные поля не обновляются.
  `physicalRaw` и `rsCatalog` — самостоятельные поля, их блокировка независима от
  производных полей. `slug`, identity, `lockedFields`, `isArchived`, `createdAt`
  автоматически не меняются. Цикл категорий, включая ручные parentId, отменяет импорт.

### Аудит и счётчики

ImportFile хранит заголовки DocType/SenderGln/ReceiverGln/Currency/DocumentNumber/
DocumentDate, кодировку и имена XML в `metadata.documents`. Для ZIP с одним XML
заполняются также отдельные поля documentNumber/documentDate/documentDateRaw;
для нескольких XML эти поля null, все заголовки доступны в массиве.

Счётчики ImportRun отражают товары, а не число созданных Brand/Category.
Те же счётчики каждого файла находятся в `ImportFile.metadata.counters`:

- `processedRecords`: прочитанные DocDetail до завершения/первой ошибки;
- `createdRecords` / `updatedRecords`: зафиксированные новые/изменённые Product;
- `skippedRecords`: идентичные дубли, записи успешного SHA и неизменившиеся Product;
- `failedRecords`: прочитанные непропущенные записи отменённого запуска;
- `errorCount`: 1 для первой ошибки запуска; на уровне файла — ошибка обработки
  этого файла. Общая ошибка публикации относится к ImportRun;
- `warningCount`: число сохранённых WARNING ImportIssue (правила EAN ниже).

Для обработанных записей выполняется processed = created + updated + skipped + failed.
Непрочитанные после ошибки записи не оцениваются. На ошибке все файлы текущей попытки
имеют FAILED; предыдущие успешные попытки остаются неизменными. Диагностика первого
конфликтного дубля содержит оба источника, хеша и обе исходные записи; первая запись
повторно читается из ZIP только при конфликте. EAN-предупреждения и ошибки
BARCODE_* сохраняются в ImportIssue с позицией и исходными значениями.

### Проверки

    node --test scripts/import/prodat.test.cjs scripts/import/prodat-import.test.cjs
    node --test scripts/import/prodat-integration.test.cjs

Integration suite использует `PRODAT_TEST_ADMIN_URL` либо URL из `.env` только для
создания отдельной БД `prodat_test_<pid>_<random>`. Пользователю PostgreSQL нужен
CREATEDB. SQL существующих трёх миграций применяется только туда; importer получает

Рабочая elektrikamarket не заполняется и не очищается.

Полный тест обоих текущих архивов, повторного импорта, отсутствия дублей и скорости

    node --test scripts/import/prodat-integration.test.cjs
    Remove-Item Env:PRODAT_FULL_TEST

Полный тест также работает исключительно во временной БД. Выводит длительность
и измеренный по контрольным точкам peak RSS процесса Node. Это локальный benchmark,
а не гарантия производительности другого сервера. Legacy `prodat-dry-run.ts` остаётся
инструментом проверки исходного XML/дублей без БД; бизнес-нормализация проверяется

## Человекочитаемые slug и одноразовый repair

`prodat-v1.1.0` использует `prodat-slug.cjs` и для создания новых записей, и для
планирования repair. Изменение версии само по себе не снимает защиту успешного SHA:
повтор исходных ZIP не исправляет slug и не перепубликует базовый каталог.
Новый слой EAN обрабатывается отдельно по маркеру возможностей (см. ниже).

Точный алгоритм:

1. Unicode NFC и lowercase. Русские буквы транслитерируются до удаления диакритики:

       а a, б b, в v, г g, д d, е e, ё yo, ж zh, з z, и i, й y,
       к k, л l, м m, н n, о o, п p, р r, с s, т t, у u, ф f,
       х kh, ц ts, ч ch, ш sh, щ shch, ъ пусто, ы y, ь пусто,
       э e, ю yu, я ya.

2. Unicode NFKD, удаление combining marks (латинские é/ü → e/u).
   Все последовательности вне `[a-z0-9]` заменяются одним `-`. Крайние дефисы
   удаляются. Основа ограничена 120 ASCII-символами; дефис в конце снова удаляется.
   Если основы нет, используется product/category/brand со стабильным суффиксом.
3. Уникальность проверяется отдельно в каждой таблице. Все существующие slug
   резервируются. Среди одновременно создаваемых записей одинаковые основы
   получают суффикс у КАЖДОГО участника: порядок записей/ZIP не выбирает победителя.
4. Суффикс Product — slugify(supplierCode), Category — slugify(sourceKey), до 48
   символов. Brand — первые 12 hex SHA-256 от точного нормализованного Brand.name
   (identity). Пустой суффикс identity заменяется первыми 12 hex её SHA-256.
5. Если итог пересёкся с существующим или другим предлагаемым slug, добавляется
   полный SHA-256 identity. После этого обязательно проверяется уникальность всего
   результата. Остаточная коллизия — ошибка до записи, без числового перебора.
6. Уже существующие записи сохраняют slug при обновлении name и остальных полей.
   Старые hash-slug не меняются обычным импортёром автоматически.

Repair предназначен строго для первоначальной загрузки: ImportRun #1, версия
`prodat-v1.0.0`, SUCCEEDED, два известных имени/SHA архивов. Другие PRODAT-запуски
допускаются только со статусом SKIPPED. Он не создаёт ImportRun/ImportFile.

Кандидат обязан иметь точное старое значение `kind-SHA256(identity)`, а не только
похожий формат. `lockedFields=['slug']`, человекочитаемые, manual и неизвестные
технические значения остаются нетронутыми. Происхождение проверяется так:

- Product: lastProdatFileId относится к первоначальным файлам, createdAt и
  lastProdatAt соответствуют первой транзакции публикации;
- Brand: связь с первоначальным Product и createdAt первой публикации;
- Category: sourceKey присутствует в RsCatalog-снимках первоначальных Product
  (у Category нет собственного createdAt/ImportFile).

Первоначальная публикация выполнена в PostgreSQL UTC. Сравнение createdAt
(timestamp без зоны) с finishedAt выполняется в SQL с явным UTC, чтобы часовой
пояс Node.js не влиял на eligibility.

Dry-run — настоящая REPEATABLE READ READ ONLY транзакция, без UPDATE и без записей
аудита. Проверяются все будущие значения с учётом неизменяемых slug. Даже старые
slug кандидатов резервируются, чтобы UPDATE не создавал промежуточных UNIQUE-конфликтов.
Вывод: counts, коллизии, 20 примеров, changed=0 и SHA-256 полного плана с его входными
данными. Это предварительный расчёт, не разрешение на применение.

    node scripts/import/prodat-repair-slugs.cjs --database-url-env DATABASE_URL --dry-run

После отдельного решения о применении используется тот же скрипт с `--apply` и
`--expected-plan <planHash из проверенного dry-run>` вместо `--dry-run`.
Без явного режима CLI завершается ошибкой; библиотечный вызов по умолчанию dry-run.

Apply повторно рассчитывает план внутри одной транзакции под общей с импортёром
advisory-блокировкой и блокировками трёх таблиц. Если план изменился — отказ до UPDATE.
Обновляется только колонка slug: updatedAt и все остальные данные сохраняются.
Любая ошибка отменяет весь repair. Повтор после успешного исправления планирует
0 изменений. Применение проверено на временной БД и затем выполнено на рабочей БД
по отдельно разрешённому плану (результат ниже).

## EAN / ProductBarcode (ean-v1)

Источник — DocDetail.EAN.Value, описание — EAN.Description; повторяющиеся Value
и Description сопоставляются по индексу. Description сохраняется в type, исходный
индекс — в sortOrder. Пустой EAN означает отсутствие штрихкодов.
Barcode остаётся строкой: никаких Number, дополнения нулями или исправления цифр.
Крайние пробелы удаляются с WARNING BARCODE_WHITESPACE и исходной строкой в details.
Неверная контрольная цифра GTIN (8/12/13/14), нестандартная длина и нецифровое значение
сохраняются с BARCODE_CHECKSUM / BARCODE_LENGTH / BARCODE_NON_DIGIT соответственно.
Пустой Value пропускается с BARCODE_EMPTY. Неоднозначная структура/пары и разные
описания одного кода у товара — ошибка, весь запуск откатывается.

Identity — (productId, barcode), Product находится по supplierCode. Повтор одной
пары не создаёт строку и даёт BARCODE_DUPLICATE; сохраняется первая позиция.
Одинаковый код у разных товаров разрешён схемой, товары не объединяются;
BARCODE_SHARED_ACROSS_PRODUCTS сообщает о каждом входящем участнике.
Существующая schema достаточна, миграция не нужна.

origin=PRODAT для новых строк. Ручные (origin=MANUAL), isLocked и отношение
Product.lockedFields=['barcodes'] защищены; отличия дают BARCODE_PROTECTED.
Обновляются только type/sortOrder незаблокированных PRODAT-строк. Исчезнувшие из
источника штрихкоды и товары не удаляются. Базовый каталог и EAN публикуются атомарно.

Защита SHA учитывает слои: старый SUCCEEDED сохраняет базовый каталог нетронутым,
но допускает однократное добавление EAN. Успех отмечается в
ImportFile.metadata.layers.barcodes='ean-v1'. Следующий тот же SHA — SKIPPED.
Изменение VERSION само по себе не снимает защиту слоя. Порядок ZIP не влияет на
каталог; принадлежность точного дубля к файлу аудита определяется первым источником.

ImportRun и metadata ImportFile: inputEntries, uniquePairs, duplicateEntries,
